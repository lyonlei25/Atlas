# 06 · 落地路线

> 不要一次铺开全套。挑**一个**最小的东西先跑通，验证「事实驱动」这套到底成不成。

---

## 从哪开始：可执行契约 + 测试驱动状态

整套体系里，这一小块**信息含量最高、最能立刻见效、最能验证内核**：

> 在你一个真实的**基础模块**和一个**业务模块**之间，跑通：
> 「接口契约做成可执行的契约测试 → 测试通过自动驱动看板状态 → 业务模块据此替换占位符」。

把这一小块跑通，你就握住了整套东西的内核（**用事实而非自陈驱动状态**），剩下的都是往外长。

**为什么是它，不是别的：**

- 它直接验证最反直觉、也最核心的那条原则：状态由事实翻牌，不由 Agent 宣布。
- 它同时触及契约、diff、看板三个关键件，是个真实的纵切。
- 它范围小，错了代价低，适合验证方法本身。

---

## 推荐推进顺序

> 这是建议次序，核心是**先有「能骗不了的事实源」，再谈用它做治理**。

1. **先有事实源**
   让 skill 能拿到 Agent 的实际 diff。没有这个，后面所有「用事实揭穿自陈」都无从谈起 —— 这是地基。

2. **再做一条可执行契约**
   挑一对真实的基础/业务模块，把它们之间的接口写成契约测试（可执行，不是文字）。

3. **接上测试驱动状态**
   契约测试通过 → 看板状态自动翻「已兑现」。这一步让你第一次看到「事实驱动状态」跑起来。

4. **接上占位符替换**
   业务模块看到事实状态才替换。验证整条「不靠通知、只认事实」的链路。

5. **加上 diff 比对**
   开工声明范围 + 收工交 diff，看板侧机械比对「声称 vs 实际」「承诺 vs 实际」，标红。这一步让你第一次看到黑盒藏的东西被自动抓出来。

6. **再往外长**
   有了内核，再逐步补 L1 的机器强制、L2 的范围冻结流程、L3 的越界处置、看板的三级可信度分层。

---

## 当前推进状态

M1 已经跑通最小可信纵切：事实源、可执行契约、测试驱动状态、占位符替换、diff 比对和基础看板都已经落地。M1 是后续开发的基线，不再继续塞新范围。

M2 启动前先做一件事：**把 Git 流程固化为里程碑前置治理**。原因是 M2 开始后，Atlas 要用自己管理自己；如果分支、PR 目标和里程碑集成线还没定，后续 dogfood 会从第一步就失真。

M2 前置 Git 流程采用：

```text
main                 # 存档主线
release              # 持续发布主线
milestone/m2-dogfood # M2 独立集成分支
feature/m2-*         # M2 feature 分支
```

完成这个前置项后，再进入 M2：Atlas dogfood。

详细开发计划见 [`07-development-plan.md`](07-development-plan.md)。

## 落地时的对应关系

本方案是蓝图，抽象概念落到你的实际工具上：

| 蓝图概念 | 落到你的环境 |
|---------|------------|
| 可执行的契约 | 你技术栈里的契约测试 / 接口测试 |
| 事实驱动状态 | CI 通过后自动更新看板状态（webhook / API） |
| 实际操作痕迹 | git diff |
| 机器强制约束 | hook / linter / CI 检查 |
| 看板 | 你选的看板工具 + skill 写入 |
| 撞线必停 | 流程上的人工确认关卡 |

---

## 一个判断标准：什么时候算「跑通了」

> 当你能做到：**一个 feature 的状态，没有任何人手动点过，纯靠测试结果翻牌；
> 而它声称做的和实际改的之间一旦有差，你不用读代码就能在看板上看到标红。**

到这一步，「用最少的人类验证换取最多的系统可信度」这套，就从理念变成了你手里跑着的东西。

---

## 不要做的事

- ❌ 一上来就建大而全的看板、定义所有字段 —— 先跑通一条纵切。
- ❌ 指望让 Agent「如实汇报」来保证质量 —— 永远拿不到可信自陈，把功夫花在事实源上。
- ❌ 把约束一股脑写进 agents.md —— 能机器强制的交给机器。
- ❌ 让 Agent 自己判断「我有没有越界」并写结论 —— 比对必须在它外面做。
