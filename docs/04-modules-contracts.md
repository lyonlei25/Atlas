# 04 · 模块解耦与契约

> **解决的是**：多个 feature 并行时撞同一个共享东西。
> **核心手段**：业务对接口编程；契约住看板（不住会蒸发的对话）；事实驱动替换。

---

## 它解决的口子

单 feature 守住之后，还剩一个口子：

> 两个 feature 都去碰同一个公共函数，撞在一起。它们各自的锚都没破，合起来那个公共函数被两种不一致的意图拉扯。

这是「多人协作不好协调」的最终形态 —— 不再是乱改的问题，而是**多个守规矩的 feature，撞在同一个共享的东西上**。

---

## 思路：把共享面从「实现」收窄到「契约」

![契约协作](04-contract.svg)

让业务 Agent **不再去碰那个公共东西**：

- 业务 Agent 不直接改基础模块，只对一个**接口**编程。
- 基础模块在接口背后自己实现。
- 业务先用**占位符**顶替，等基础模块好了再替换。

> 这样多个业务 feature 哪怕都依赖同一个基础能力，碰的也只是那个约定死的接口，而不是它的内部实现。
> **共享的东西从「实现」收窄成「契约」，共享面一窄，撞车自然就少。**

每个模块有自己的 `agents.md`，装这个模块对外承诺什么、内部约定什么。模块大了各自有 agents.md，是必然要走的。

---

## 但有个东西变了：约定接口的是两个 Agent

人的世界里「团队 A 和 B 约定接口，各写各的」能成，是因为**约定接口的是人，人能为约定负责、能记住、能在它不合理时回来重新谈**。

但这套里，约定接口的是两个 Agent，于是老问题换张脸回来了：

> **Agent 没有跨 session 记忆，而接口契约恰恰是个需要长期被记住、被遵守的东西。**

如果约定只活在那两个 session 的对话里 —— session 一结束，它就蒸发了。下次基础模块的 Agent（很可能是全新 session）来开发，**不知道之前约定过什么**，按自己的理解实现一个。等业务 Agent 来替换占位符时，发现对不上。

> 这不是谁犯错，是这个约定根本没有一个它们都看得见、都改不动的地方住着。

---

## 所以：接口契约必须住进看板

> 业务 Agent 和基础 Agent 不在对话里约定接口，而是在**看板上注册一份接口契约**。
> 一旦注册，它就独立于任何 session 存在 —— 基础 Agent 下次来照着它实现，业务 Agent 替换占位符也照着它对。

**契约不再活在会蒸发的对话里，活在那个谁都改不动的共享大脑里。**

---

## 三条硬规则

### 规则一 · 契约要「可执行」，不要纯文字

> 一份接口契约，如果只是 wiki 上一段文字说「接受 X 返回 Y」，它会漂移 —— 实现变了，文字没变。
> 如果这份契约**同时是一组会运行的契约测试**，它就没法对实现撒谎：实现一旦不符，测试就红。

**契约越「可执行」越不会成谎言；越「纯文字」越会漂移。往可执行那一侧拼命拉。**

### 规则二 · 任何单个 Agent 不能单方面改契约

基础 Agent 开发到一半，很可能发现约定的接口不合理、实现不出来、得改。这时：

> 如果它能自己改契约，就破坏了业务 Agent 赖以工作的前提（业务那边占位符是照旧契约写的）。
> **这跟 L3「自以为必要地越界」是一模一样的病，只不过共享的东西是契约本身。**

所以：

> 它发现契约有问题，**不能自己改，得撞线停下来，把「这个接口我实现不了，需要改成 X」抛回去**，让人（或双方）重新约定、重新焊死契约，两边再按新契约走。

接口契约是整个体系里「撤不回、别人依赖」的**最高级别**的东西，所以受的约束也最硬。

### 规则三 · 替换扳机挂在「事实」上，不挂在「通知」上

「通知业务模块，业务模块直接把占位符替换为正式接口」—— **「直接替换」四个字是雷。**

> 如果是基础 Agent 自己说「我按契约做好了，你来换吧」，那又是黑盒自陈：
> 它真心觉得做好了，业务 Agent 信了直接换，结果实现跟契约有出入，业务模块当场就坏，而且坏得很隐蔽（接口层面的不一致）。

正确做法：

> 替换的触发条件得是一个**事实**，不是一句话。最自然的形态：**针对这份契约的契约测试通过了。**

1. 基础模块实现完 → 跑契约自带的测试
2. 测试通过 → 看板状态自动翻「契约已兑现」（事实）
3. 业务 Agent 看到这个事实状态 → 才替换占位符

**业务换上去的，是被验证过确实符合契约的，不是基础 Agent 嘴上保证的。**

---

## 一个迟早撞上的深层问题：契约演化

接口契约本身也要演化（基础能力升级、业务需求变，v1 → v2）。可一旦某个接口被很多业务模块用占位符顶着依赖，**改一个契约就会同时震动所有依赖它的业务模块。**

这是软件工程最古老的难题 —— **依赖管理与契约版本演化** —— 在 Agent 体系里的最终形态，也正好接回最初的诉求「持续开发、项目变大也不失控」。

> 人的世界用版本号、废弃周期、兼容性承诺来管，靠大量人的协调和纪律。
> 在这套里：当一个契约要演化，怎么让所有依赖它的业务 Agent 知道、并有序跟上，而不是某天突然集体对不上？

这个口子留给落地时按你的实际规模处理 —— 但原则不变：**契约的每次演化也是一个显式的、记录在看板上的、由事实（新契约测试）驱动的动作，绝不能是某个 Agent 单方面悄悄改。**

---

## 一句话

> 把共享的东西从「实现」收窄成「契约」，契约住进看板而非对话，
> 做成可执行的、谁都不能单方面改的、由测试通过来驱动替换的东西。
