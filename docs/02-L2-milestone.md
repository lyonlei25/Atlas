# 02 · L2 里程碑级治理

> **时间尺度**：中期、一段时间内冻结。
> **防的是**：范围蔓延。
> **核心手段**：冻结 —— 把「想」和「做」在时间上彻底切开。

---

## 这一层的反直觉选择：在 AI 时代主动用瀑布

里程碑启动时，需求已经讨论完、feature 已经拆完，才让 Agent 进场。这看似保守，实则正中要害。

**为什么瀑布在这里是对的？**

> Agent 最危险的恰恰是「边干边想」 —— 它会在开发中途自作主张地扩大范围、顺手改不该改的、把一个小需求做成大重构。

而「想完再做」的本质是：

> **把「想」和「做」在时间上彻底切开：想的阶段人来主导，做的阶段才让 Agent 进场，且进场时范围已经焊死。**

这正好卡住了 Agent 最容易失控的那个点。Agent 在一个边界明确、不需要它做大决策的盒子里，是最可靠的；一旦让它自己决定「要不要顺便把这个也改了」，它就开始攒黑盒。

> 所以瀑布在这里不是保守，是**用流程把「全局决策」这件最不该交给 Agent 的事，挡在 Agent 进场之前。**

---

## 流程全貌

![里程碑流程](02-milestone.svg)

左边「想」是人的地盘，Agent 不进场；中间一道**范围冻结**的闸；右边「做」才让 Agent 进来，且只能在焊死的范围里填。

---

## 「想」阶段（人主导，Agent 不进场）

1. **需求充分讨论** —— 把要做什么彻底谈清楚，边界明确。
2. **Feature 拆分完毕** —— 拆成一个个边界清晰的盒子。
3. **每个 Feature 焊好「范围 + 验收标准」** —— 这就是 L3 的**硬锚**，Agent 改不动。
4. **识别共享依赖 → 约定接口契约** —— 注册进看板，独立于 session 存在（详见 [04](#modules)）。

---

## 范围冻结：这一层最该守的纪律

里程碑一旦启动，那条「范围线」必须是 **Agent 改不动**的。

> Agent 在开发 feature 时如果发现「还需要做 X」，X 不能直接就做 ——
> 得回到看板上变成一条新的、待人确认的东西，而不是它当场吞进当前 feature。

**冻结的范围，Agent 只能往里填，不能自己往外扩。**

---

## 关键设计：范围蔓延要「吐回去」，不能「吞掉」

开发中冒出来的、超出当前范围的发现，有三种命运，**只有一种是对的**：

| 做法 | 后果 |
|------|------|
| ❌ Agent 当场默默做了 | 范围被顶破，且藏在「实现需要」名义下，不可见 |
| ❌ 直接丢弃 | 真问题丢失 |
| ✅ 吐到看板，成为下一轮输入 | 范围蔓延被接住，变成有记录、待决策的东西 |

> 不是默默吞掉，也不是当场就做，而是**吐到看板上成为下一轮的输入**。

---

## 这一层往看板接什么

- 里程碑下的 feature 列表、每个 feature 的状态
- **开发中冒出来的、超出当前范围的发现** —— 让它有地方落，变成下一轮的待决策项

---

## 一句话

> L2 用流程把「全局决策」挡在 Agent 进场之前。
> 范围焊死后，Agent 只能往里填；想往外扩，必须吐回看板让人决策，不能自己吞。
