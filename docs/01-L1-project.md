# 01 · L1 项目级治理

> **时间尺度**：长期、几乎不变。
> **防的是**：漂移（文档会撒谎）。
> **核心手段**：让规则不可违反，而不是让 Agent 记住。

---

## 这一层管什么

长期不变、所有人所有 Agent 共享的东西：

- 通用规则、技术栈约定
- Git 规范（提交格式、分支命名）
- 全局性的架构决策（一旦定了所有人都得遵守）
- 目录结构、不许碰的区域

这些东西的特点：**变化最慢，但最容易过期。**

---

## 核心原则：分清「机器强制」与「软约定」

L1 的关键不是「写全」，是把约束分成两类：

### 第一类 · 能机器强制的 → 不写进给 Agent 读的文档

凡是能用 hook / CI / 类型系统卡死的，就别写进文档让 Agent 背：

| 约束 | 强制方式 |
|------|---------|
| Git 提交格式、分支命名 | commit hook / CI 校验 |
| 代码风格 | linter / formatter + pre-commit |
| 不许碰的目录 | CI 检测改动路径，违规即拦 |
| 类型契约 | 类型检查，编译期拦截 |

> **为什么**：这直接回应了「约束加重 Agent 心智负担」的担忧。
> 真正减负的方式不是少约束，是**把约束从「它要记」挪成「机器替它挡」**。
> 它的上下文里就不用背这些 —— 机器替它记着，它撞墙了自然知道。

### Atlas 当前的 Git 需求约束

Git 流程属于 L1：它变化慢、所有人共享，而且最好由机器挡住错误目标分支。

Atlas 从 M2 前置开始采用这条主线：

```text
main
  └─ release
       └─ milestone/<id>-<name>
            └─ feature/<milestone>-<feature-id>
```

职责边界：

- `main` 是存档主线，只接收已发布或已归档的稳定快照。
- `release` 是持续发布主线，代表当前可发布、可演示的稳定状态。
- `milestone/*` 是里程碑集成分支，从 `release` 稳定点切出。
- `feature/*` 只能从所属里程碑分支切出，并合回该里程碑分支。
- 里程碑整体验证通过后，再一次性合入 `release`。

这不是额外流程负担，而是把 L2 的「范围冻结」落到 Git 上：里程碑分支就是那个能独立验证、独立回滚、独立发布的边界盒子。详细规则见 [`git-engineering-management-standard.md`](git-engineering-management-standard.md)。

### 第二类 · 没法机器化的 → 才放进文档，且要少

品味层面的东西（比如「本项目偏好组合而非继承」）没法做成自动报错，只能写文档。但：

> **要少，少到 Agent 每次都能扛得住。**

文档越长，它每条都得现场扛，越抓不住重点。

---

## 根目录 agents.md 该放什么

根 agents.md 是「Agent 的宪法」，但它只该装**第二类**（软约定）+ 指路：

应当包含：
- 项目是什么、当前在哪个阶段（指向看板）
- 那些没法机器强制的品味/偏好（精简）
- 去哪找什么（模块 agents.md 在哪、契约在看板哪里）
- 全局性的、所有人必须遵守的架构决策

不应当包含：
- 任何能被 lint / CI / 类型强制的规则（交给机器）
- 长篇大论的风格指南（机器化或砍掉）
- 会过期的具体实现细节（那是模块级的事，且会漂移）

> 模块大了之后，根目录一份 agents.md 扛不住，各模块要有自己的 agents.md。
> 这是必然要走的 —— 详见 [04 模块解耦](#modules)。

---

## 这一层往看板接什么

**项目的当前真实状态**（变化最慢，是看板最稳的底座）：

- 现在在哪个里程碑、整体进度
- 全局性的架构决定（定了所有人都得遵守的那种）

---

## 一句话

> L1 的全部功夫，是把「会过期、会被 Agent 读到旧版本」的规则，
> 尽量变成「违反就自动报错」的形式 —— 让机器记，而不是让 Agent 背。
