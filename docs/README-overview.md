# AI-Native 工程治理方案

> 一套面向「人 + Agent 协同开发」的工程治理蓝图。
> 读者既是人，也是 Agent —— 所以全部用 Markdown，两边都能读。

---

## 这套方案要解决什么

两个最初的诉求：

1. **持续开发** —— 项目逐步变大，Agent 不失控。
2. **团队协作** —— 多人多 Agent 参与，能协调。

往下挖，它们最终落到同一个答案上：**在一群没有记忆、互相不透明、还会美化自己的黑盒之间，建立一个可信的共享现实。**

落到 Atlas 自身开发时，还要补上一条工程需求：**里程碑必须能被独立查看、验证、回滚和发布**。因此 Git 流程本身也是治理对象，不只是团队习惯：

- `main` 作为存档主线，只保存已发布或已归档的稳定快照。
- `release` 作为持续发布主线，承载当前可发布、可演示的稳定状态。
- 每个里程碑从 `release` 的稳定点切出独立 `milestone/*` 分支。
- feature 只能从所属里程碑分支切出，并合回该里程碑分支。
- 里程碑整体验证通过后，再一次性合入 `release`。

这让「范围冻结」同时存在于看板和 Git 里：看板定义边界，分支结构承载边界，CI / PR 门禁负责挡住越界。

---

## 一句话内核

> **控制点全部放在 Agent 外面。**
> 它内部不可控，但它能祸害的范围、以及你能否收拾，都在外面。
> 共享的 / 别人依赖的 / 撤不回的东西 → 放进谁都改不动的地方，用「事实」而非「自陈」驱动状态。
> **不赌 Agent 不犯错，赌系统接得住它犯错。**

## 怎么读

- **想理解为什么** → 先读 00，它解释了后面所有设计的动机。
- **想直接看怎么做** → 跳到 01–05，每层都是独立的。
- **想动手** → 先看 06 理解落地顺序，再看 07 按里程碑推进。

> 本方案是**蓝图**，讲架构、原则、决策，不绑定具体技术栈。落地时把抽象的「契约测试」「事实驱动状态」对应到你自己的工具即可。
